# Phase 6 import behavior

Imports accept JSON schema versions 1 and 2. Workout `unit` is required and may be `lb` or `kg`; bodyweight and circumference units are `bodyweightUnit` (`lb` or `kg`) and `bodyMeasurementUnit` (`in` or `cm`). Weights are converted to canonical pounds and measurements to canonical centimeters. A valid `YYYY-MM-DD` calendar date is required for every observation. Missing body units use the compatibility conversion defaults, but their stored input-unit provenance remains unknown and the preview reports that assumption.

The importer keeps workout notes, source-unit provenance, warm-up flags, and an explicitly supplied `rir` from 0 through 10. It never invents an RIR when the source omits it. Body imports preserve notes and unit provenance when declared. Unsupported source fields are ignored; no machine profile or other metadata is inferred.

Import is additive. For workouts with an `externalId`, that ID is the source identity: reusing it skips the import even if the source later changes the workout's notes, date, sets, or RIR. The ID must not contain the reserved `::` delimiter. Deleted workouts keep their receipts as tombstones. To deliberately restore a deleted workout, provide a new external ID. Without an external ID, the importer uses a content fingerprint, which skips the same content already owned by the importing account. An identical workout from another account does not suppress the import. Older receipts whose external IDs contained `::` remain unchanged for reconciliation and may have ambiguous identity boundaries.

Bodyweight and measurement rows for the same date are combined into one check-in. An occupied body-check-in date is skipped as a whole, preserving the existing record instead of merging or overwriting it. If the observation is later deleted, explicitly importing the source again can fill the now-empty date; body imports do not keep source-identity tombstones. Repeated body rows for one date within a file use the last valid row of that kind and produce a preview warning.

The cloud import is bound to the account that initiated it. A cloud transaction commits the batch atomically and returns actual inserted body check-ins, workouts, and sets, plus skipped body dates/workouts. A thrown transaction reports failure and commits no part of that batch. On local storage, import requires one unambiguous current account; ambiguous legacy ownership is rejected rather than guessed.
